**Stacked PRs** are small pull requests that build on each other: the first one targets `main`, and each next one targets the branch of the pull request below it. Since October 2026, **GitHub supports stacked pull requests natively** on every github.com plan: install the `gh stack` extension for GitHub CLI, run `gh stack init`, add one branch per layer with `gh stack add`, then `gh stack submit` to open and link the pull requests.

Managing [code reviews](https://axolo.co) efficiently can make or break your team's productivity, and stacking is one of the best ways to keep pull requests small. By leveraging **stacked pull requests**, your team can streamline collaboration, improve code quality, and adhere to best practices.

Whether you're working on a large refactor or a multi-step feature, **PR stacking** ensures that each step is reviewed independently, reducing bottlenecks and making it easier to identify potential issues early. But how can your team get the most out of this workflow? From understanding **how to create a PR in GitHub** to integrating tools like Axolo, we’ll guide you through the strategies and techniques to implement **git stacked PRs** effectively.

Throughout this guide, you’ll discover:

- When to use **stacked PRs in GitHub** to enhance your workflow.
- How **stacked pull requests** enable quicker, more focused reviews.
- Tips for aligning your workflow with **GitHub pull request best practices** for faster merges and better code quality.

A Stacked Pull Request (PR) is a development workflow strategy where multiple smaller PRs are opened in a specific sequence, each one building upon the previous. This approach allows for easier code review, as each PR contains a manageable chunk of changes, making it simpler for reviewers to understand the context and impact. Stacked PRs are particularly useful in larger projects where a single PR could become overwhelming to review.

If you'd like to learn more about PRs, I invite you to read [GitHub pull request workflow](https://axolo.co/blog/p/why-your-pull-requests-are-taking-forever).

### When and why should you use stacked PRs?

By breaking down large changes into smaller, manageable units, **stacked PRs** offer numerous advantages over monolithic pull requests. But when exactly should you use stacked pull requests, and why is this strategy beneficial? Let’s explore.

#### When to Use Stacked PRs

1. **Complex Features**: When implementing a feature that requires multiple independent steps, using **stacked pull requests** allows each step to be reviewed and merged sequentially. This approach ensures incremental progress and reduces the risk of errors.
2. **Large Refactoring**: For significant refactors, **git stacked PRs** make it easier to isolate changes, ensuring each piece is tested and reviewed thoroughly without overwhelming reviewers.
3. **Collaboration Across Teams**: When multiple teams or developers work on interconnected changes, **stacked PRs** help maintain a clear dependency chain, avoiding merge conflicts.
4. **Iterative Development**: In agile workflows, where feedback and iterative improvements are common, **PR stacking** ensures that every small change is handled independently while maintaining the integrity of the base branch.

#### Why Use Stacked PRs

1. **Clearer Code Reviews**: **GitHub stacked diffs** allow reviewers to focus on specific parts of the code, making reviews faster and more focused.
2. **Reduced Risk**: Smaller, isolated changes mean fewer surprises during integration. By using **stack PR** practices, the likelihood of bugs and regressions decreases.
3. **Efficient Collaboration**: Teams can parallelize their work, and ensures that dependent branches are handled logically and systematically.
4. **Better Code Quality**: Best practices, like keeping changes small and self-contained, are naturally supported by stacking PRs. This ensures maintainability and readability.

You have two options: GitHub's native stacks, or plain Git branches.

### Option 1: native stacked pull requests with gh stack

GitHub made stacked pull requests [generally available on October 6, 2026](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/), on all github.com plans. Stacks are created with the `gh stack` extension for GitHub CLI ([quickstart](https://docs.github.com/en/pull-requests/get-started/stacked-prs-quickstart)):

```bash
# Install the extension once
gh extension install github/gh-stack

# Start a stack and commit the first layer
gh stack init
git add .
git commit -m "Add the database migration"

# Add the next layer on top of the stack
gh stack add api-endpoint
git add .
git commit -m "Add the API endpoint"

# Push every branch, then open and link the pull requests
gh stack push
gh stack submit

# See the stack, its pull requests and their status
gh stack view
```

How merging works, according to [GitHub's documentation](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs):

- Each pull request shows only its own layer's diff and is reviewed on its own.
- Pull requests merge **from the bottom up**. Merging a pull request in the middle merges everything below it; the ones above stay open and are retargeted automatically.
- Merge commit, squash and rebase are supported, and stacks work with the merge queue.
- Branch protection rules, such as CODEOWNERS approvals, apply to every pull request in the stack.

Limits to know: all branches must be in the same repository (no cross-fork stacks), GitHub Desktop does not support stacks, and GitHub Enterprise Server will get the feature in an upcoming release.

### Option 2: stack pull requests with plain Git

Without the extension, you can still stack by hand: each pull request uses the branch below it as its base.

1. **Create the first branch** from `main`, commit, push, and open a pull request against `main`.
   ```bash
   git checkout main
   git checkout -b feature-branch
   git commit -am "Add the database migration"
   git push -u origin feature-branch
   ```
2. **Create the dependent branch** from the first one, push it, and open a pull request whose **base is `feature-branch`**, not `main`.
   ```bash
   git checkout -b feature-branch-2
   git commit -am "Add the API endpoint"
   git push -u origin feature-branch-2
   gh pr create --base feature-branch
   ```
3. **Merge from the bottom up.** When the first pull request merges, retarget the next one to `main` and rebase it if needed. This manual rebasing is exactly what `gh stack` and the tools below automate.

## How to create stacked merge requests on GitLab

GitLab calls this workflow **stacked diffs**. The GitLab CLI has an experimental `glab stack` command ([documentation](https://docs.gitlab.com/user/project/merge_requests/stacked_diffs/)): `glab stack create` starts a stack, `glab stack save` adds a change, and `glab stack sync` pushes the branches and opens one merge request per change, each targeting the branch of the previous one. GitLab marks it as experimental and not ready for production use. Git Town, listed below, also stacks branches on GitLab.

## Best practices for reviewing stacked PRs

- **Keep each layer small**: one logical change per pull request, with a description that says what it depends on.
- **Review from the bottom up**: the lowest pull request merges first, so review it first.
- **Label manual stacks**: without native stacks, label the pull requests as stacked to avoid an early merge into `main`.
