A good Git commit message has a short subject line (about 50 characters, imperative mood), a blank line, then a body that explains what changed and why, wrapped at 72 characters. To make your whole team follow that format, save a template file and point Git to it with `git config --global commit.template ~/.gitmessage.txt`: Git then pre-fills your editor with it on every `git commit`.

## Git commit message template (copy and paste)

Save this file as `~/.gitmessage.txt`. Lines that start with `#` are comments: Git removes them from the final message.

```plaintext
# <type>(<optional scope>): <subject, imperative, max 50 chars>
# Example: fix(auth): reject empty passwords on login

# Body: what changed and why (not how). Wrap at 72 characters.

# Footer: issue references, breaking changes, co-authors.
# Refs: #123
# BREAKING CHANGE: <what breaks and how to migrate>
# Co-authored-by: Name <email@example.com>
```

Then tell Git to use it:

```bash
# For all your repositories
git config --global commit.template ~/.gitmessage.txt

# Or for the current repository only (path relative to the repository root)
git config commit.template .gitmessage.txt
```

How the template behaves, per the [git commit documentation](https://git-scm.com/docs/git-commit):

- It only appears when Git opens your editor, so with a plain `git commit`. It has no effect with `git commit -m` or `-F`.
- If you close the editor without changing the template, Git aborts the commit.
- `git commit --template=<file>` uses another template for a single commit.

You can also add team-specific reminders to the template, for example how to reference tickets or which <a href="https://axolo.co/blog/p/pull-request-vs-merge-request">pull request or merge request</a> the commit belongs to.

## How to write a multi-line commit message with git commit -m

You do not need the editor for a subject plus a body. Each `-m` becomes its own paragraph, separated by a blank line:

```bash
git commit -m "fix(auth): reject empty passwords on login" \
  -m "The login endpoint accepted an empty password and returned a 500. Validate the field before calling the auth service." \
  -m "Refs: #123"
```

## Part 1: Understanding Git Commit Messages

### What is a Git Commit Message?

A Git commit message is a short note that goes with each commit in a Git repository. It shows what was changed and explains why those changes were made, serving as an important piece of documentation in your version control process.

- **Definition and Purpose**: Every commit message clarifies the motivation behind a particular change, helping current and future developers understand the reasoning behind edits when they look back at the project’s history. <a href="https://www.atlassian.com/git/tutorials/saving-changes/git-commit" rel="nofollow noopener noreferrer">Atlassian Git Tutorials</a>

- **Anatomy of a Commit Message**: Generally, a well-written commit message has three parts: a subject line, a body, and a footer. The subject line sums up the changes, the body dives into the details, and the footer can include extra data like issue IDs or references. <a href="https://www.conventionalcommits.org/en/v1.0.0/" rel="nofollow noopener noreferrer">Conventional Commits</a>

Providing this level of detail is particularly helpful when dealing with complex projects, since it clarifies why certain paths were taken. Maintaining informative commit messages makes your version history a valuable resource for the entire team.

### Why Git Commit Messages Matter

Beyond day-to-day coding tasks, commit messages play a significant role in the health of a software project:

- **Streamlining Code Reviews**: Explaining the scope and purpose of changes helps reviewers provide better feedback.
- **Easier Debugging and Troubleshooting**: A well-documented commit history accelerates the process of finding when and how bugs were introduced.
- **Project Onboarding**: New contributors gain insights into the evolution and decision-making behind the code.
- **Workflow Automation**: Many CI/CD pipelines rely on commit messages for actions like generating changelogs or deploying features.

By consistently writing informative commit messages, developers keep the repository’s history an asset rather than a hindrance.

## Part 2: Structure of a Git Commit Message

### Subject Line

Each commit message starts with a subject line that briefly captures the essence of your changes. It gives teammates a quick snapshot of the commit’s purpose.

- **Concise Summary (50 characters max)**: Keep your subject line short—ideally no more than 50 characters—so it’s easy to read in various Git tools. <a href="https://cbea.ms/git-commit/" rel="nofollow noopener noreferrer">How to Write a Git Commit Message</a>

### Body

The body of your commit message can include technical details, design reasons, or other relevant background that shaped the changes you made. <a href="https://www.freecodecamp.org/news/writing-good-commit-messages-a-practical-guide/" rel="nofollow noopener noreferrer">Writing Good Commit Messages</a>

- **Referencing Issues or Pull Requests**: If possible, mention any related issues or PRs to provide additional context and keep the broader discussion linked. <a href="https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls" rel="nofollow noopener noreferrer">Referencing Issues in Commits</a>

- **Paragraph Breaks**: Use distinct paragraphs for different points to maintain clarity. This makes it easier for others to scan and understand your message. <a href="https://github.com/angular/angular/blob/main/CONTRIBUTING.md#-commit-message-format" rel="nofollow noopener noreferrer">Commit Message Guidelines</a>

### Footer

In the footer, you can list any relevant metadata:

(See also <a href="https://git-scm.com/docs/git-commit#Documentation/git-commit.txt--s" rel="nofollow noopener noreferrer">Sign-off in Commit Messages</a> for more details.)

- **Signed-off-by**: Some teams require a “Signed-off-by” line in the footer. This is particularly important for projects adhering to the Developer Certificate of Origin (DCO). <a href="https://git-scm.com/docs/git-commit#_signing_off_commits" rel="nofollow noopener noreferrer">Git Documentation on Sign-offs</a>

## Part 3: Writing Effective Git Commit Messages

### Tips for Crafting Clear and Concise Messages

Clear and concise commit messages can make your codebase significantly easier to maintain and review. Below are some suggestions:

- **Be Specific**: Avoid vague text. Summarize the change precisely and mention why it was needed. <a href="https://github.com/erlang/otp/wiki/Writing-good-commit-messages" rel="nofollow noopener noreferrer">Effective Commit Messages</a>
- **Active Voice & Present Tense**: Opt for a direct, present-tense style (e.g., “Fix bug” rather than “Fixed bug”). It’s more straightforward and common in version control logs. <a href="https://cbea.ms/git-commit/#active" rel="nofollow noopener noreferrer">Active Voice in Commit Messages</a>

### The Imperative Mood

Many teams recommend writing commit messages in the imperative mood. It keeps messages consistent and clearly states the action the commit will take when applied.

- **Why Imperative Mood Matters**: Short commands like “Add” or “Fix” set an easy-to-read standard. <a href="https://cbea.ms/git-commit/#imperative" rel="nofollow noopener noreferrer">Imperative Mood in Git Commit Messages</a>
- **Examples**: “Add new feature,” “Fix layout bug,” etc. <a href="https://www.conventionalcommits.org/en/v1.0.0/" rel="nofollow noopener noreferrer">Sample Commit Messages</a>

Crafting strong commit messages blends clarity, brevity, and structure. Below are several tried-and-true best practices.

### Keep Messages Short but Descriptive

Aim for a concise message that still conveys the essential changes. Many teams recommend a subject line of up to 50 characters.

### Separate Subject and Body with a Blank Line

Placing a blank line between the subject and the body ensures better readability and compatibility with various Git tools.

### Use the Body to Explain the “What” and “Why,” Not the “How”

Focus on the reason behind the change rather than the implementation details. The code itself shows how something is done.

### Reference Issues and Pull Requests

Linking an issue or PR number helps with traceability, so everyone knows the broader discussion.

### Capitalize the Subject Line (Unless You Use Conventional Commits)

A capital letter makes each subject look cleaner. Teams using Conventional Commits usually keep the description lowercase after the type (`fix: handle empty input`). Pick one style and stick to it.

### Avoid Ending the Subject with a Period

It’s unnecessary, and skipping it maintains a uniform style.

### Wrap the Body at 72 Characters

A 72-character line width is typical, keeping messages neatly formatted in various tools.

#### Examples of Good vs. Bad Commit Messages

- **Good**:

  ```plaintext
  Fix null pointer exception in login

  Users who submitted the login form without credentials triggered a
  null pointer error. Validate the fields before processing the request.

  Fixes #123
  ```

- **Bad**:

  ```plaintext
  fixed bug
  ```

## Part 7: Common Pitfalls and How to Avoid Them

Even with guidelines, it’s easy to slip into bad habits. Here are some frequent pitfalls:

### Vague Commit Messages

Phrases like “update code” or “fix stuff” don’t explain anything. Be precise about the change and its motivation.

### Overly Detailed Commit Messages

On the flip side, massive blocks of text can obscure the main idea. Strike a balance between clarity and brevity.

### Ignoring the Subject Line

Always give a clear, concise subject line. This is the first thing people see and should summarize the commit at a glance.

By avoiding these common errors, you’ll maintain a clean, navigable history.

## Part 8: Git Commit Message Conventions

Conventions add clarity to your project’s commit history, simplifying how changes are categorized and understood.

### Conventional Commits

[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) (current version: 1.0.0) is the most widely used commit message convention. The format is:

```plaintext
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

- `fix:` is a bug fix and maps to a PATCH release in Semantic Versioning.
- `feat:` is a new feature and maps to a MINOR release.
- A `!` after the type or scope (`feat(api)!:`), or a `BREAKING CHANGE:` footer, marks a breaking change and maps to a MAJOR release.
- Other types are allowed. The common set, from the Angular convention used by commitlint's default config, is `build`, `chore`, `ci`, `docs`, `style`, `refactor`, `perf` and `test`.

### Semantic Commit Messages

Align your commit messages with **semantic commits**. Tools such as semantic-release read Conventional Commits to bump the version and write the changelog automatically. <a href="https://semver.org/" rel="nofollow noopener noreferrer">Semantic Versioning</a>

### Customizing Commit Message Guidelines for Your Team

Adopt existing formats or tailor them to your workflow. The goal is to keep messages uniform and easy to parse. A **commit convention** can unify everyone’s approach.
