## 1. Code review in GitLab

### How to do a code review in GitLab

GitLab has a built-in review flow on every tier (Free, Premium and Ultimate), on GitLab.com and GitLab Self-Managed. Here is how it works, according to the <NoFollowLink url='https://docs.gitlab.com/user/project/merge_requests/reviews/'>GitLab merge request reviews documentation</NoFollowLink>:

1. **Request a review.** The author assigns reviewers in the **Reviewers** section of the right sidebar, or with the `/assign_reviewer @username` quick action. The merge request then appears in the reviewer's **Review requested** list.
2. **Read the context.** The reviewer reads the description and the existing comments, then opens the **Changes** tab to see the diff.
3. **Start a review.** On the first comment, select **Start a review** instead of **Add comment now**. The comment stays unpublished and the sidebar shows that your review is in progress. Each following comment is saved with **Add to review**.
4. **Suggest changes.** Use single-line or multi-line suggestions so the author can apply your proposal directly from the GitLab UI.
5. **Submit the review.** Select **Your review**, check your pending comments, write an optional summary, and pick an outcome:
   - **Approve**: leave feedback and approve the changes.
   - **Comment**: leave general feedback without approving or blocking.
   - **Request changes**: block the merge request until the author addresses your feedback (the blocking part requires GitLab Premium or Ultimate).
6. **Re-request a review.** After pushing fixes, the author selects the **Re-request a review** icon next to the reviewer's name, or uses `/request_review @username`.

When you submit, GitLab publishes all your comments at once and sends a single email to the people following the merge request, instead of one notification per comment.

### Why approving a merge request in GitLab is important

Approvals make sure that someone other than the author has looked at the change before it is merged:

- In **GitLab Free**, every user with at least the Developer role can approve a merge request, but approvals are optional and do not block merging.
- In **GitLab Premium and Ultimate**, you can make approvals required, set the number and type of approvers, and require approval from Code Owners for the files they own.

Merge request approvals can be configured per project and at the group level. Administrators of GitLab Self-Managed Premium and Ultimate instances can also configure approvals for the entire instance.

#### Merge request approval rules in GitLab

Approval rules (GitLab Premium and Ultimate) set the minimum number of approvals required before code can be merged, and which users can approve. For example:

- Require one approval from the backend team on every merge request.
- Require Code Owners to approve changes to the files they own.
- Require a security team member to approve changes that introduce potential vulnerabilities (GitLab Ultimate).

Configure them in **Settings > Merge requests > Merge request approvals**. You can also prevent authors from approving their own merge requests and decide whether approvals are reset when new commits are pushed.

#### How to approve a merge request in GitLab

When an eligible approver opens a merge request, GitLab shows an **Approve** button in the merge request widget. You can also:

- Approve while submitting your review (the **Approve** outcome).
- Use the `/approve` quick action in a comment.
- Revoke your approval later with **Revoke approval**.

A merge request can be merged once it has the required approvals, unless another merge check blocks it: merge conflicts, unresolved threads, a failed CI/CD pipeline, or a pending change request.

You can find more detailed information in the <NoFollowLink url='https://docs.gitlab.com/user/project/merge_requests/approvals/'>Merge Request Approvals</NoFollowLink> section of the GitLab documentation.

### GitLab default reviewers

#### How to set default reviewers in GitLab

GitLab does not have a "default reviewers" list per project, but there are four ways to get the same result:

1. **Automatic reviewer assignment (GitLab Premium and Ultimate).** Since GitLab 19.1, a project Maintainer can turn on **Settings > Merge requests > Automatic reviewer assignment > Automatically assign all code owners as reviewers**. GitLab then assigns the Code Owners of the changed files when a merge request is created in a ready state, or when a draft is marked as ready. It needs a CODEOWNERS file (see below) and skips merge requests that already have a reviewer.
2. **Recommend Reviewers Flow (GitLab Premium and Ultimate, GitLab Duo Agent Platform).** Generally available since GitLab 19.5, it recommends the minimum number of reviewers needed to satisfy each approval rule, based on availability, workload and time zone. You still choose who to assign.
3. **A merge request description template.** Quick actions in description templates run when the merge request is created, so a default template containing `/assign_reviewer @username` assigns that reviewer every time (the author needs permission to set reviewers).
4. **An external tool.** On GitLab Free, our free [Auto Assign Reviewer for GitLab](https://axolo.co/auto-assign-reviewer-for-gitlab) reads your CODEOWNERS file and assigns reviewers on new merge requests.

The full details are in the <NoFollowLink url='https://docs.gitlab.com/user/project/merge_requests/reviews/automatic_reviewer_assignment/'>automatic reviewer assignment documentation</NoFollowLink>.

#### GitLab Code Owners for merge requests

Code Owners is a GitLab Premium and Ultimate feature. Create a CODEOWNERS file to specify which users or groups own which files and directories in a repository. GitLab looks for the file in three places:

- In the root of your repository
- In the `.gitlab/` directory
- In the `docs/` directory

Enter rules that follow these patterns:

```
## Code Owners for a file
filename-path @username1 @username2

## Code Owners for a directory
directory-path/ @username1 @username2

## All group members as Code Owners for a file
filename @groupname

## All group members as Code Owners for a directory
directoryname/ @groupname

## Set up group members as Code Owners for the entire repository
* @groupname
```

### GitLab code review without a merge request

Reviews, approvals and review status live on merge requests, so there is no full review flow outside of them. You still have two options:

- **Comment on a commit.** Go to **Code > Commits**, select a commit, and add a comment or start a thread. This works for a quick question on code that is already on a branch.
- **Open a merge request for the review only.** To review existing code, for example an old feature or a whole repository, create a branch from an earlier commit (or an empty branch), then open a merge request from the branch you want reviewed into it. Reviewers get the full diff, threads and approvals. Close the merge request without merging when the review is done.

### GitLab Duo code review

GitLab can also review merge requests with AI. Assign `@GitLabDuo` as a reviewer, or use `/assign_reviewer @GitLabDuo`, and GitLab Duo posts review comments on the diff. Two versions exist:

- **Code Review Flow**, the agentic version, available on every tier and billed with GitLab Credits.
- **GitLab Duo Code Review**, the original version, for users with the GitLab Duo Enterprise add-on (GitLab Premium and Ultimate).

Both can run automatically when a merge request is created, and both accept custom review instructions. An AI review is a good first pass, not a replacement for a teammate who knows the code. See the <NoFollowLink url='https://docs.gitlab.com/user/project/merge_requests/duo_in_merge_requests/'>GitLab Duo in merge requests documentation</NoFollowLink>.

### GitLab code review workflow

1. Push your changes to a branch, from your terminal or the GitLab interface.
2. Open a merge request. Mark it as a draft while it is not ready, so nobody reviews unfinished work.
3. Mark it as ready and request reviewers (or let automatic reviewer assignment do it).
4. Wait for the CI/CD pipeline to pass.
5. Reviewers start a review, then submit it with **Approve**, **Comment** or **Request changes**.
6. The author resolves the threads, pushes fixes, and re-requests a review.
7. Once the required approvals are in and every merge check passes, merge.

Most delays happen between steps 3 and 5, while the merge request waits for someone to notice it. A [GitLab Slack integration](https://axolo.co/gitlab-slack-integration) such as Axolo brings review requests, comments and pipeline results into Slack so reviewers see them without checking GitLab.

### GitLab merge request best practices

- **Keep merge requests small.** A diff that can be read in one sitting gets a faster, better review.
- **Write a useful description.** Explain why the change is needed and how to test it. A default description template makes this a habit.
- **Use drafts.** Draft merge requests cannot be merged and signal that the work is not ready for review.
- **Let the pipeline run first.** Reviewers should not spend time on code that fails its tests.
- **Require approvals on protected branches** (Premium and Ultimate), and require Code Owners approval for sensitive paths.
- **Resolve every thread.** Turn on "All threads must be resolved" in the merge checks so no comment is lost.
- **Use suggestions.** A suggested change is quicker to apply than a comment describing it.

## 2. GitLab review apps

Built-in GitLab review apps have four main characteristics:

- By spinning up a dynamic environment for your merge requests, you can automatically provide a live preview of changes made in a feature branch.
- Allow designers and product managers to see your changes without having to check out your branch and test them in a sandbox environment.
- Are completely integrated with GitLab's DevOps LifeCycle.
- Give you the freedom to deploy your changes wherever you want.

### How do review apps work?

A Review App is a branch-to-environment mapping. Access to the Review App is made available via a link on the branch's merge request.

The following is an example of a merge request with a dynamically set environment. A branch was successfully built in this example and deployed in a dynamic environment accessible by selecting the View app.

Following the addition of Review Apps to your workflow, you follow the branched Git flow. That is, push a branch and let the runner deploy the Review App based on the dynamic environment job's script definition. Then, the runner will build and deploy your web application.

To view the changes live, select the link in the merge request related to the branch. You have now set up a new review environment!

If you're interested, you can learn more in the dedicated <NoFollowLink url='https://docs.gitlab.com/ci/review_apps/'>GitLab Review App Documentation</NoFollowLink> section.

### Why are review apps important?

#### GitLab review apps for developers

Developers can begin collecting feedback much sooner. Submit a merge request and test your changes in real-time. When you push to master, you'll know that your changes have gone through CI testing as well as a live review where the team can ensure that everything works as expected.

#### GitLab review apps for the design, product, and marketing team

Giving feedback to designers, product managers, marketing colleagues, and others has never been easier. To preview changes, you won't need to check out branches or set up a staging environment. With Review Apps, you can see the live changes by clicking a link. Hopefully, this means you'll be able to provide more timely and accurate feedback.

## 3. GitLab CI/CD & automatic deployment

GitLab developed an internal CI/CD tool for software development following the continuous methodologies:

- Continuous Integration (CI)
- Continuous Delivery (CD)
- Continuous Deployment (CD)

Continuous Integration works by pushing small changes to your application’s codebase hosted in a Git repository, and, to every push, run a pipeline of scripts to build, test, and validate the code changes before merging them into the main branch.

Continuous Delivery and Deployment consist of a step further CI, deploying your application to production at every push to the default branch of the repository.

These methodologies allow you to catch bugs and errors early in the development cycle, ensuring that all the code deployed to production complies with the code standards you established for your app.

For more detailed information on GitLab CI/CD, you can watch a <NoFollowLink url='https://www.youtube.com/watch?v=1iXFbchozdY'>Demo: CI/CD with GitLab</NoFollowLink> made by the GitLab team or surf through the <NoFollowLink url='https://about.gitlab.com/blog/2016/08/05/continuous-integration-delivery-and-deployment-with-gitlab'>CI/CD Documentation</NoFollowLink>.
